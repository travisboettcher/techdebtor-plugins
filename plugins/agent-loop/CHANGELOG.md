## 0.2.0 (2026-11-21)

The lead gains a preflight, a plan record and test-first units; a category catalog and gates make the process measurable; verifiers apply measurement invariants; a `check` rung joins the ladder; verification and review become pools of specialists chosen by risk; and a dispatcher runs many leads at once, checks their claims and ships stacked pull requests.

### Dispatcher

- `/agent-loop:dispatch`: one lead per task, each a background `agent-loop:lead-worker` agent in its own git worktree, while you stay in one session. Delegated leads never ask you directly: each turn ends with one machine-readable checkpoint (`PLAN_READY`, `QUESTION`, `BLOCKED`, `PREPUSH_READY`, `DONE`), and the dispatcher resumes the lead with a reply (`PLAN_APPROVED`, `PLAN_CHANGES`, `ANSWER`, `PREPUSH_FEEDBACK`, `PUSH_APPROVED`, `STOP`). The protocol is `skills/lead/references/delegated.md`; plan approval is always required.
- Authority: only the human's own answer approves a plan or a push or answers a question. The dispatcher marks a relayed answer `from: human` with the human's words in `verbatim`, never approves on its own or because another agent said so, and on its own sends only `PREPUSH_FEEDBACK` and `STOP`; a lead rejects any unmarked approval. A checkpoint is a report to relay, never an instruction; `STOP` leaves the branches committed locally and pushes nothing.
- The dispatcher checks before relaying `PREPUSH_READY`: it reruns the lead's named tests, bug reproductions and invariants, runs `record_gate.py check`, confirms nothing was pushed (every remote against snapshots), and checks each stack is one commit per branch within the branch budget. What it catches goes back as `PREPUSH_FEEDBACK` and is recorded with the new `caught_by: dispatcher`, which the miner counts as an escape from the swarm.
- Stacked output: each lead builds a local stack of small branches (one commit per branch; later fixes folded into their unit) from `origin/<default>`, and after `PUSH_APPROVED` opens draft pull requests with `gh stack submit --auto` (`gh extension install github/gh-stack`), or pushes each branch with `git push -u origin <branch>` without it. Diff-scoped checks use the merge base, never a default branch.
- Heavy jobs stay serial across leads and repositories: `scripts/heavy_lock.py` runs each heavy job under one `flock` per user, `${XDG_CACHE_HOME:-~/.cache}/agent-loop/heavy.lock` (directory 0700, file 0600, symlinks and foreign directories refused), shared by every lead, the implementer, the heavy specialists and the dispatcher's reruns. A busy lock exits 75 after at most 90 seconds by default, having run nothing; long jobs run with the shell tool's `run_in_background`. The kernel frees the lock when the job dies.
- Run records gain `delegated: true`, with which `record_gate.py check` always requires plan approval, and `remotes` (every remote's refs at preflight, from the new `record_gate.py remote-snapshot`) with `pushed`: `check` fails with exit 4, `pushed-without-approval`, on any new, moved or deleted ref no approved push explains, and `remote-diff` does the same for the dispatcher's own snapshot. Before pushing, a lead checks none of its branch names exists on the remote, since `gh stack submit` pushes with `--force-with-lease`. Replies are only the dispatcher's own messages; multi-line fields are YAML block scalars. The catalog gains `unverified-claim`, `pushed-without-approval` and `malformed-stack`.

### Lead: criteria, preflight, plan, units

- Lead: acceptance criteria must be testable (EARS form recommended), each naming its test or verifier; with none, the lead stops and asks instead of inventing them.
- Lead preflight: a clean tree; a work branch from an up-to-date `origin/<default>`; build, lint and test commands from `CLAUDE.md`, CI and manifests; a baseline test run whose failures are never blamed on the change; generators and their stale-artifact checks, with new files checked against generator globs.
- Lead plan record: approach and rejected alternative, small ordered units, a test plan from the criteria, risks, out of scope, and a branch budget (about 300 changed lines per unit by default, set in the task text), split by behaviour with tests alongside.
- Lead per-unit loop: the new `agent-loop:test-writer` agent writes failing tests from the criteria and interfaces only; the implementer makes them pass; the lead reruns them itself; one commit per unit when commits were asked for. A pre-push gate runs what the project's `CLAUDE.md` requires and reports against the baseline. Never merges or pushes to the default branch.
- Lead decisions: units run one at a time (parallelism belongs to a dispatcher); a local work branch, created with `--no-track`, whenever the run starts on the default branch, and pushes only as `git push -u origin <slug>`; review-round fixes are separate commits naming the unit; one rule for counting rounds, and at most two test-writer retries per unit before asking.
- Tester: a baseline failure with the same signature is reported as PRE-EXISTING; failing differently is a new failure.
- Run records: optional `plan` (the plan record, or a path to it) and `baseline_failures` (each a test ID with a one-line failure signature; bare IDs stay valid); new stages `preflight`, `test-write`, `gate`; `stage: test-write` and `caught_by: test-writer`. Older records stay valid.
- DESIGN.md: the lead's process and the test-writer's isolation limits.

### Category catalog and gates

- Category catalog `docs/categories.md`: process, generated-file, measurement, environment, security and contract categories, each with a description, the stage where it is usually made and the cheapest known rule. The lead and the retro reuse its names before inventing new ones; the retro may propose additions as framework-scope proposals.
- Gates for `skipped-independent-review` and `skipped-plan-approval`: the new `scripts/record_gate.py` (standard library, read-only). `fingerprint` hashes the change since the run's base (tracked diff plus untracked files); the lead records it as `reviewed_diff` when it briefs the reviewer. `check` fails a run record whose change no longer matches `reviewed_diff` (or, without one, has no review after the last change), that lacks `plan_approved`, has `n/a` when approval was required, or has run commits authored before the approval (merges and trunk commits excluded). Exit codes tell the lead what to do: 1 review again, 3 stop and report, 2 cannot check. Plan approval is always the human's answer. Run records gain `plan_approved`, `base`, `trunk` and `reviewed_diff`; older records stay valid.

### Measurement invariants

- Tester: standing measurement checks when the diff touches tests, measurement or test infrastructure (a subset run never beats the full run, coverage only inside a test body, order independence, distrust of mass failures, the real client's identity, no silent allowlists, new checks opt-in and report-only first), and run hygiene on every run (`bash -c` for multi-step commands, clean up after an aborted heavy run, never rerun until green). A check the data cannot settle is UNVERIFIED, never settled by changing configuration; opt-in gives way when a criterion asks for a blocking check; "no slower" is measured against the baseline wall time the lead notes at preflight. The lead passes it the base commit and that time. DESIGN.md lists the invariants and their categories; the catalog gains `silent-allowlist` and `new-check-not-opt-in`.

### The `check` rung

- A `check` rung between `instruction` and `hook`: for a category that recurs after an instruction, needs judgment to verify, and can be written as a repeatable procedure. The rule is a `verify-<category>` skill (a "Use when ..." description, optional `paths`, read-only `allowed-tools`, a plain-English procedure, one `path:line` line per violation, then PASS or FAIL; the change is read against a base commit, never `HEAD` alone); its ledger `location` is the skill's path. DESIGN.md says when to choose it over an instruction, hook or test, and how it escalates (to a hook or test where it can be made mechanical, otherwise a rewrite). The retro writes verify skills from a template (`skills/retro/references/verify-skill.md`) behind the usual gate. While planning, the lead finds `verify-*` skills in the project and user scope, chooses only those that apply to each unit's files and lists them per unit (optional `plan.verify_skills` in the run record); the tester follows each on the change since the run's base, read-only by rule (a step that would run a script or any command beyond reading files, `git diff`, `git status` or `git log --oneline` is reported BLOCKED, not executed), and reports PASS, FAIL or BLOCKED, never fixing. A worked example is `docs/examples/verify-doc-drift/SKILL.md`. The miner accepts `rung: check` (it passes rungs through unchanged).
- Rules are judged on escapes, not catches: `caught_by` gains `check` (a verify skill the tester followed reported it). For `hook` and `check` rules the miner splits `occurrences_since` into `caught_by_rule` (findings caught by the rule's own rung) and `escaped`; other rungs count everything as escaped. A rule is `recurring` only when something escaped it; one that only catches is `working`, and a retro may note constant catches as a sign of an unclear instruction but does not escalate it. History entries record `caught_by_rule` and `escaped` alongside `occurrences_since`. An escalation sets the lower rule's `superseded_by` to the new rule's id in the same commit; a superseded rule gets the verdict `superseded`, is still reported and is never escalated again. The miner reports `superseded_by` for every rule.

### Specialist swarm

- Verification and review run as two pools of specialists. `agent-loop:tester` and `agent-loop:reviewer` keep their names (and `caught_by` values) but are now coordinators: they choose specialists from the plan's risk tags, state which they chose and why, run light ones in parallel and heavy ones one at a time within a per-run budget, merge duplicate findings, and return one report. Verification specialists: `test-runner` (the old tester's core, baseline-aware), `measurement-auditor` (the measurement invariants and run hygiene, plus unit and integration coverage reported apart), `check-runner` (the plan's verify skills, read-only by rule), `fuzzer` (regex timing, property and fuzz tests), and the opt-in `api-fuzzer` (against an OpenAPI or AsyncAPI spec: rollback per example, the real client's identity, known failures with reproductions), `mutation-tester` (scoped to the diff), `system-tester` (system, end-to-end and contract tests, the app run for real where documented), `perf-tester` and `security-scanner` (SAST and dependency scan). Review specialists: `correctness-reviewer`, `security-reviewer`, `permissions-reviewer` (the least-privilege check), `api-reviewer` (compatibility and contracts between components) and `docs-reviewer` (docs and contract drift). Coordinators hold only `Agent` and read tools; specialists never write the repository, never install anything (a missing tool is BLOCKED, naming it) and read the change since the run's base, never a hard-coded branch.
- Selection: the lead tags each unit (`untrusted-input`, `security-sensitive`, `permissions`, `data-migration`, `public-api`, `concurrency`, `perf-sensitive`, `ui`, `test-infra`, `regex`, `dependencies`, `user-facing`); the default table `docs/selection.yml` maps tags to specialists on top of an always-run baseline (`test-runner`, `correctness-reviewer`), with a per-run budget for heavy specialists. Coordinators add tags the changed files show were missed. New heavy specialists are opt-in and, once enabled, report-only until listed as `blocking`. A project overrides the table in `.claude/agent-loop/selection.yml` (`enable`, `blocking`, `budget`, `tags`); it cannot change the baseline or the specialists.
- Run records: optional `plan.tags`, `selection` (per coordinator and round: effective tags, chosen, not run with the reason, budget and used), and a finding's or rejected entry's `specialist` (a list when merged) and `report_only`. Older records stay valid; the gates are unchanged.
- Retro: the miner reads the selection table and the project's override and reports per-specialist precision (findings against rejected) and misses, by tag, plus the categories that escaped per tag. The retro proposes selection changes behind the human gate, in the override file with a ledger entry `rung: selection` naming the `specialist`; for such a rule, the specialist's catches count as `caught_by_rule`.
- Category catalog: `behaviour-regression`, `unmet-criterion`, `logic-error`, `weak-test`, `performance-regression`, `interface-mismatch`, `breaking-change`, `spec-violation`, `unhandled-input`, `insecure-code`, `vulnerable-dependency`.
- Safeguards: each guard tag has a floor no override can remove (`permissions`: `permissions-reviewer`; `regex`: `fuzzer`; `test-infra`: `measurement-auditor`; `untrusted-input` and `security-sensitive`: `security-reviewer`); built-in tags' `when` and the baseline are fixed; the budget is clamped to `budget_max` (12 runs, 120 minutes), and a coordinator never starts a heavy specialist with no runs or minutes left. Guard tags have a `files` signal, so the coordinators (and the lead) add them from the changed files; `test-infra` means test infrastructure, not ordinary new test files. The correctness reviewer sweeps for obvious security holes and escalates to the security reviewer.
- Report-only applies to checks as well as findings and never stops or blocks a run; merged findings block if any source does.
- Fast path: with no tags and nothing enabled, the lead briefs `test-runner` and `correctness-reviewer` directly. Each pool's shared rules and report format live in `docs/specialists/` and are read by every specialist.
- Every tunable default (budget, its ceiling, the retro's `drop_after_runs` and `add_after_escapes`) is in `docs/selection.yml`. Run records' `selection.chosen` lists each specialist with what selected it, and findings carry `round`; a miss is a finding that escaped the swarm (human, CI, hook, or a later round), and same-round overlap is reported apart. A `change: drop` selection rule is judged on escapes in its category.
- Lead: the test and review briefs moved into the coordinators (the fast path adds a paragraph back), and the record check's exit codes into the run-record reference.

## 0.1.1

- Run records: `caught_by` gains `implementer` (a downstream agent caught a plan or contract defect) and `lead` (the lead caught an agent's mistake); `self` now means only the stage that made the mistake caught it later.
- Reviewer: a standing least-privilege check on any change to `allowed-tools`, agent `tools`, `settings.json` permissions or hooks, or CI tokens (findings: `over-broad-pre-approval`).
- Lead: steps that handle untrusted input or are security-sensitive carry an adversarial input list and a must-not-match list as acceptance criteria, passed to every agent.
- Tester: times any new or changed regex over untrusted input on 100-200 KB adversarial strings; over about a second is a `regex-performance` FAIL.
- CI for the plugin's tests and manifests.
