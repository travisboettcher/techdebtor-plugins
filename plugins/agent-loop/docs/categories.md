# Finding categories

The starting vocabulary for a run record's `category` (see `DESIGN.md`). A category is the unit a retro counts, so the same mistake must get the same name in every run. Before inventing a category, reuse one from this catalog, the rules ledgers, or earlier run records; invent a new kebab-case one only when none fits, and name the kind of mistake, not the incident. A retro may propose adding a recurring new category here, as a framework-scope proposal behind the human gate.

Each entry: the category, what goes wrong, the `stage` where it is usually made (the run record's `stage`: where the mistake was made, not who caught it; the lead's own mistakes, preflight included, are `plan`), and the cheapest rule known to stop it. A rule naming a part of this plugin (a gate, a preflight step, a specialist's check) is already applied there, for the units whose risk tags select that specialist (`docs/selection.yml`); the others are what a retro should propose when the category recurs.

## Process

| Category | What goes wrong | Usually made | Cheapest known rule |
|---|---|---|---|
| `skipped-plan-approval` | Implementation started, or was committed, before a plan that needed the human's approval was approved (in a delegated run, a `PLAN_APPROVED` reply marked as the human's own answer; an agent's approval never counts). | plan | Gate: `scripts/record_gate.py` fails without `plan_approved`, and on commits authored before it; `delegated: true` always requires it (DESIGN.md, "Gates"). |
| `skipped-independent-review` | The change was reported done without an independent review of the final diff (self-review, or fixes made after the last review). | plan | Gate: `scripts/record_gate.py` fails unless the change still matches the fingerprint taken for the last review (`reviewed_diff`). |
| `branch-over-budget` | A unit or branch went well over the branch budget, or was split into a code part and a tests part. | plan | Split by behaviour with tests alongside; the lead checks `git diff --stat` per unit. |
| `stale-trunk` | Branched from, or compared against, a stale local default branch instead of `origin/<default>`. | plan | Preflight: fetch, then branch from `origin/<default>` with `--no-track`. |
| `scope-mismatch` | The change does more or less than the task asked: unrequested changes, or part of the task silently dropped. | implement | Criteria name every requested behaviour and the plan lists what is out of scope; the correctness reviewer's scope check. |
| `unverified-claim` | A report claims a result that was never run, or that a rerun contradicts: tests passing, a bug reproduced or fixed, an invariant holding, a check run. | plan | Rerun every claim before passing it on: the lead reruns its agents' claims, and the dispatcher reruns a delegated lead's before relaying `PREPUSH_READY`. |
| `pushed-without-approval` | A branch was pushed or a pull request opened without the human's approval (in a delegated run, a `PUSH_APPROVED` reply marked as the human's own answer). | plan | Push only after that approval, with explicit branch names. Gate: `scripts/record_gate.py` compares every remote with the snapshot taken at preflight (exit 4), and the dispatcher with its own before relaying `PREPUSH_READY`. |
| `malformed-stack` | A stack of branches is not one commit per branch, each on the branch below it: an empty branch, several commits, a merge, or a branch based on something else. | plan | Fold a later round's fix into its unit's commit; the dispatcher counts each branch's commits before relaying `PREPUSH_READY`. |

## Generated files

| Category | What goes wrong | Usually made | Cheapest known rule |
|---|---|---|---|
| `generated-artifact-not-regenerated` | A generator's input changed without regenerating its checked-in or CI-used output, so CI or the build breaks. | implement | Preflight finds each generator and its stale-artifact check; the pre-push gate runs them. |
| `new-file-matches-generator-glob` | A new file matched a generator's input glob and silently became, or broke, a generated job or artifact. | implement | Preflight records each generator's globs; every new file is checked against them. |
| `generated-file-hand-edit` | Generated output was edited by hand instead of its source, so the next regeneration loses the edit. | implement | A project hook refusing edits to files headed `Generated by`; the implementer's rule against editing generated files and the correctness reviewer's scope check. |

## Measurement

| Category | What goes wrong | Usually made | Cheapest known rule |
|---|---|---|---|
| `measurement-attribution-leak` | A measurement credits the wrong scope, such as coverage collected during setup or import and given to whichever test ran first. | implement | The measurement auditor: a subset run never beats the full run; count only what runs inside a test body. |
| `shared-state-false-failures` | Tests share state (a database session, a global, a temporary directory), so one failure poisons the rest: a wall of false failures, or a test that fails in the suite and passes alone. | implement | Isolate state per test (roll back per example); the measurement auditor: in a mass failure, investigate the first failure; failing in the suite and passing alone is reported, never rerun until green. |
| `wrong-auth-identity` | A test or check runs as a convenient identity (an admin, a machine token) instead of the role real clients use, so its results do not match theirs. | implement | Test as the real client's role and credentials (the measurement auditor). |
| `silent-allowlist` | Known failures are skipped, deselected or allowlisted without being listed, so a real regression hides among them. | implement | List every known failure with a reproduction (the measurement auditor). |
| `new-check-not-opt-in` | A new check runs by default locally or blocks CI from the start, slowing the default run or failing work it was not meant to gate yet. | implement | New checks are opt-in locally and report-only in CI at first (the measurement auditor). |

## Environment

| Category | What goes wrong | Usually made | Cheapest known rule |
|---|---|---|---|
| `shell-portability` | A multi-step command depends on the interactive shell (word splitting, globbing, builtins) and does something else there, such as running a whole suite. | implement | Run multi-step scripts with `bash -c`, or as a file with a shebang (every verification specialist's run hygiene). |
| `leftover-resources` | An aborted or finished heavy run left containers, worktrees, temporary databases or processes behind. | test | After any aborted heavy run, remove what it started and check that nothing is left (every verification specialist's run hygiene). |

## Security

| Category | What goes wrong | Usually made | Cheapest known rule |
|---|---|---|---|
| `redaction-gap` | A secret-shaped value gets past redaction or sanitising: glued to a neighbour, quoted, split across a boundary. | implement | An adversarial input list and a must-not-match list as acceptance criteria (the lead's plan step). |
| `over-broad-pre-approval` | A permission entry (`allowed-tools`, agent `tools`, settings, CI token) is wider than needed: a wildcard that admits a writing flag, or a path a cloned repo could plant. | implement | The permissions reviewer's least-privilege check. |
| `regex-performance` | A regular expression applied to untrusted or unbounded input backtracks badly on adversarial strings. | implement | The fuzzer's timing check on 100-200 KB adversarial input. |
| `unhandled-input` | An input the code crashes on or mishandles instead of rejecting cleanly: huge numbers or bad enums and IDs reaching a query, an unknown ID crashing instead of a not-found. | implement | An adversarial input list as acceptance criteria; the fuzzer, and the API fuzzer against a spec. |
| `insecure-code` | Code an attacker can abuse: injection, unsafe deserialisation, path traversal, a missing authorisation check, weak crypto. | implement | The security reviewer; static security rules (the security scanner) where the project has them. |
| `vulnerable-dependency` | A dependency with a known vulnerability is added or kept by the change. | implement | A dependency scan (the security scanner) where the project has one. |

## Contract

| Category | What goes wrong | Usually made | Cheapest known rule |
|---|---|---|---|
| `contract-gap` | The contract, plan or brief does not say what an agent needed (an interface, an edge case, a format), so it had to guess. | plan | Agents stop and report a gap or conflict instead of guessing (the implementer's deviations, the test-writer's missing interfaces); the lead fixes the plan. |
| `contract-self-contradiction` | The contract or brief says two incompatible things, so any implementation breaks one of them. | plan | Check each new rule against the existing rules it touches before writing it down. |
| `doc-drift` | A change updated one description of a behaviour (a skill, an agent prompt, the README, the design) and left another saying something else. | implement | Search for every other place that states the changed behaviour and update it in the same change. |

## Behaviour

| Category | What goes wrong | Usually made | Cheapest known rule |
|---|---|---|---|
| `behaviour-regression` | The change breaks behaviour that worked on the base: a test that passed there fails now, or a caller breaks. | implement | Run the project's tests against the baseline (the test runner); a failure with a new signature is the change's. |
| `unmet-criterion` | An acceptance criterion the change does not satisfy, or a test that does not prove what its criterion says. | implement | Every criterion names its verifier; the test runner and the correctness reviewer check each one. |
| `logic-error` | Wrong logic the tests did not catch: an unhandled branch or error path, off-by-one, null or empty cases, a race, a leak. | implement | The correctness reviewer; then a test for the case. |
| `weak-test` | A test that passes whatever the code does: it asserts nothing, or asserts something else than it seems (`assert x == None if c else y` parses as a conditional). | test-write | The test-writer confirms each test fails first; mutation testing scoped to the diff (the mutation tester). |
| `performance-regression` | The change is slower or larger than the baseline or a stated limit. | implement | Measure against the baseline on the same machine (the performance tester). |

## Test levels

The levels (`unit`, `component`, `contract`, `integration`, `service`, `system`) and the rule behind these categories, proving each behaviour at the lowest level that can prove it, are in `DESIGN.md` ("Test levels").

| Category | What goes wrong | Usually made | Cheapest known rule |
|---|---|---|---|
| `wrong-test-level` | A behaviour is proved at a higher level than the lowest that can prove it: logic or an edge case tested only through an integration or system test, including logic among changed lines that only integration tests cover. Slow, brittle, and out of reach of mutation testing. | plan | Each criterion in the test plan gets a target level, the lowest that can prove it, and the test-writer writes at it; the test strategist checks each criterion's level. |
| `missing-contract-test` | An interface between components (or a public one others consume) changes and no contract test covers it, so each side passes its own tests and they fail together. | plan | A contract-level criterion for every boundary a unit touches; the contract tester for any unit tagged `public-api`. |
| `missing-test-level` | A criterion's planned target level has no test, or (report-only) a level the change's risk tags call for has none: an integration test for code that talks to a real collaborator, a system test for a user path. Contract tests have their own category, `missing-contract-test`. | plan | Map each unit's tags to the levels they call for when writing the test plan; the test strategist flags a missing level. |
| `unverified-stub` | A stub a test at any level runs against (a wire stub, a fake server, a mock of another service) is written by hand, not generated from or verified against a contract, so the test passes against behaviour the real collaborator does not have. | test-write | Generate stubs from contracts (consumer-driven contract stubs, a contract stub runner, mocks driven by the API spec), or verify them against the provider; the contract tester checks stub provenance at every level (the `test-stubs` tag), the service tester for its own service tests. |
| `inverted-pyramid` | The suite is top-heavy, mostly system or end-to-end tests (an ice-cream cone), so it is slow and brittle and still misses what lower levels would catch. A property of the whole suite, so always report-only. | test-write | Add tests at the lowest level that can prove a behaviour, and move logic into pure code; the test strategist reports the shape (count and run time per level, at the base and now). |

## Interfaces

| Category | What goes wrong | Usually made | Cheapest known rule |
|---|---|---|---|
| `interface-mismatch` | Two components disagree about an interface (a field, a format, an order, an error), so each passes its own tests and they fail together. | implement | A contract test between the components (the contract tester); the API reviewer and the system tester. |
| `breaking-change` | A public interface changed incompatibly without the version, deprecation or migration path its users need. | implement | The API reviewer, for any unit tagged `public-api` or `data-migration`. |
| `spec-violation` | Output breaks its published spec or schema: null where the schema says non-nullable, a missing field, an undocumented status. | implement | Fuzzing against the spec (the API fuzzer); a schema check in the tests. |
