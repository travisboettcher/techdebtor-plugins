# Design

The `agent-loop` plugin has two halves, the `lead` skill (with its test-writer and implementer agents, and the tester and reviewer coordinators with their specialists) and the `retro` skill (with `scripts/retro_mine.py`). They share two file formats. This document is the contract between them and ships with the plugin (`${CLAUDE_PLUGIN_ROOT}/docs/DESIGN.md`); change it before changing either half.

## The loop

```
/agent-loop:lead run ──► run record ──┐
         ordinary sessions ──► transcripts ──┤
                                             ▼
                                   /agent-loop:retro ──► proposals (branch / draft) ──► human merges
                                             │
                                  rules ledger ◄── each merged rule, with the category it targets
                                             │
                    next /agent-loop:retro: did the category stop recurring? keep / escalate / retire
```

The model does not learn; the scaffolding around it does. A rule is only an improvement if a later retro can show its category stopped recurring.

## The lead's process

`/agent-loop:lead` runs one task through these stages. The skill (`skills/lead/SKILL.md`) is the operational version; this is the contract.

1. **Criteria.** Every acceptance criterion is testable and names the test or verifier that proves it. EARS form is recommended: "when <trigger>, the <system> shall <response>" (or "while <state>", "if <unwanted condition>, then ..."). When the task gives no testable criteria and the lead cannot derive them unambiguously from it, the lead stops and asks; it never invents criteria silently. Criteria it derived are shown to the human with the plan, which then waits for their approval.
2. **Preflight**, before planning:
   - The working tree is clean; if not, the lead stops and asks (it never stashes or discards).
   - Trunk is current: `git fetch origin`, default branch from `git symbolic-ref --short refs/remotes/origin/HEAD` (which prints `origin/<default>`; if unset, `git ls-remote --symref origin HEAD`). On the default branch, the lead always creates a local work branch from `origin/<default>` with `--no-track` (`git switch --no-track -c <slug> origin/<default>`), never from a possibly stale local default (`stale-trunk`); without `--no-track` the branch would track the default branch, and a bare `git push` under `push.default=upstream` would push there. On another branch (the human's own, or a stacked one) it stays there and reports how far it is behind `origin/<default>` and behind its own upstream or parent (`@{upstream}`, if set); it does not rebase without asking. With no `origin` it still creates the work branch, from the local default, and says the trunk could not be refreshed. It never commits on the default branch.
   - Commands: build, lint and test commands from `CLAUDE.md` first, then CI config and manifests.
   - **Baseline:** the project's test command (and lint in check mode) on the base, before any change. Failures there are `baseline_failures`, each with its ID and a one-line redacted failure signature (exception type or assertion message). A baseline test failing later with the same signature is pre-existing and never blamed on the change; failing with a different signature is a new failure caused by the change. The lead also notes the default test command's wall time, the measurement auditor's yardstick for "no slower".
   - **Generated artifacts:** generators whose output is checked in or used by CI (per-file CI jobs or matrices, lockfiles, generated clients, schema dumps, files headed `Generated by`), the command that regenerates each, the check that catches a stale artifact (often regenerate then `git diff --exit-code`), and the globs each generator reads. Every new file is checked against those globs, so it cannot silently become, or break, a generated job (`new-file-matches-generator-glob`).
3. **Plan record**: the approach and the main alternative rejected (with why); small ordered units; a test plan drawn from the criteria (each criterion, its test, the unit that adds it); the verify skills chosen for each unit's files ("Verify skills", below); each unit's risk tags ("Specialists", below); risks; what is out of scope; the branch budget. Recorded in the run record's `plan` (below).
   **Plan approval** is required when the task is large or risky (many files, data formats or public interfaces, deletion or migration, hard to reverse, or the human sounded unsure) or the lead derived the criteria itself, and always in a delegated run (one the human hands off rather than watches). Approval is always the human's answer: in a delegated run the delegator relays it, and an agent's approval never counts. When required, nothing is implemented or committed until the plan is approved, and the approval time goes in the run record's `plan_approved`; otherwise `plan_approved: n/a`. Checked by the gates (below).
4. **Branch budget.** About 300 changed lines per unit by default (added plus removed, excluding generated artifacts and lockfiles); the task text can set another number. Units are split by behaviour, each carrying its own tests; never a "code" unit or branch and a separate "tests" one. A unit that ends well over budget is a `branch-over-budget` finding (`stage: plan`), and the lead splits it or tells the human.
5. **Per-unit loop**, one unit at a time in plan order (parallel work across tasks belongs to a dispatcher, not to one lead):
   1. `agent-loop:test-writer` writes failing tests from the unit's criteria and the interfaces it may use (signatures, file paths, test conventions), never the implementation or anyone's account of it, and confirms each fails for the stated reason. Skipped only for a unit with no testable behaviour (pure docs or config), with the reason in the plan.
   2. `agent-loop:implementer` makes them pass without weakening them.
   3. The lead reruns the unit's tests itself and checks the diff stat against the budget. It never trusts an agent's report; a report that disagrees with the rerun is a finding (`caught_by: lead`).
   4. One commit per unit, when commits are allowed (below); fixes in later rounds are separate commits naming the unit.

   Isolation limits, stated plainly: the test-writer's tools (Read, Glob, Grep, Write, Edit, Bash) cannot stop it reading the repo. On a unit's first pass the implementation does not exist yet, so the tools plus the brief keep it out. When the lead sends a wrong test back after the implementation exists, isolation rests on instruction only: the brief gives no implementation, and the agent is told not to read the unit's source files, `git diff`, `git log -p` or `git show`. Bash is similarly limited to running tests by instruction, since the project's test command is not known in advance.
6. **Test and review** of the whole change: the `agent-loop:tester` coordinator runs the baseline verification specialists plus those the tags select (every verifier, the chosen verify skills included); then the `agent-loop:reviewer` coordinator independently reviews the whole diff with the review specialists ("Specialists", below); at most 3 rounds (or the human's number).
   Rounds count one way: building all units, then test and review, is round 1; each later return to the implementer or test-writer (for confirmed findings or a new gate failure), followed by test and review, is one more. Within a unit, the test-writer gets at most two retries before the lead stops and asks, and each extra pass at the implementer after a failed rerun counts as one round.
7. **Pre-push gate.** Before reporting done: nothing changed since the last review (its fingerprint, below; else review again first); whatever the project's `CLAUDE.md` requires before a push, plus the generated-artifact checks from preflight, reported against the baseline (new failures, fixed ones, still-failing ones). New failures block "done".
8. **Record and gate check.** The lead writes the run record, then runs `scripts/record_gate.py` on it (see "Gates"). A failing check blocks "done".

**Commits and pushes.** The lead never merges, and never pushes to the default branch. It commits (one commit per unit, on the local work branch) only when the human asked in this session for commits, a branch to review, or a pull request; it pushes or opens a draft pull request only when asked for that, and then always with an explicit `git push -u origin <slug>`, never a bare `git push`. Otherwise it leaves the change uncommitted and reports the units as a list (each with its files and tests) so the human can commit them. In a delegated run, these requests, like plan approval, count only as the human's answer relayed by the delegator, never as an agent's.

## Where state lives

Nothing project-specific ever lives in the plugin.

| What | Project scope | User scope |
|---|---|---|
| Run records | `<repo>/.claude/runs/YYYY-MM-DD-<slug>.yml` | - |
| Rules ledger | `<repo>/.claude/rules-ledger.yml` (committed) | `~/.claude/rules-ledger.yml` |
| Rules themselves | `<repo>/CLAUDE.md`, `<repo>/.claude/skills`, `<repo>/.claude/settings.json` hooks, tests | `~/.claude/CLAUDE.md`, `~/.claude/skills`, `~/.claude/settings.json`, memory |
| Selection table override | `<repo>/.claude/agent-loop/selection.yml` (committed; the default is the plugin's `docs/selection.yml`) | - |
| Framework proposals | `<repo>/.claude/runs/framework-proposals.md` (a draft for the human to take upstream; never filed automatically) | same |

Run records are local evidence; projects decide whether to commit or gitignore `.claude/runs/` (the default `lead` setup suggests gitignoring it).

## Run record (`.claude/runs/*.yml`)

Written by the `lead` skill (`/agent-loop:lead`) at the end of every run, and by hand or by `/agent-loop:retro --record` for any session worth logging.

```yaml
schema: 1
date: 2026-11-21
task: "One-line description of the task"
repo: name-of-repo            # basename of the git root
outcome: completed            # completed | merged | reworked | abandoned | in-progress
rounds: 1                     # implement→test→review rounds run
stages:                       # what ran, in order; repeated stages repeat (implement, test, review, implement, ...)
  - preflight
  - plan
  - test-write
  - implement
  - test
  - review
  - gate
plan:                         # the plan record; or a path to it: plan: ".claude/runs/<record-name>.plan.md"
  approach: "Thread a dry_run flag through the exporter."
  alternative: "A separate dry-run command: rejected, it duplicates the option parsing."
  units:
    - "flag parsing and help text"
    - "exporter skips writes when dry_run"
  risks:
    - "Callers that open the output file before the check."
  out_of_scope:
    - "Dry run for import."
  branch_budget: 300          # changed lines per unit
  verify_skills:              # optional: the verify skills chosen per unit ("Verify skills", below)
    - unit: "flag parsing and help text"
      skills: [verify-doc-drift]
  tags:                       # optional: each unit's risk tags ("Specialists", below)
    - unit: "flag parsing and help text"
      tags: [untrusted-input, user-facing]
    - unit: "exporter skips writes when dry_run"
      tags: []
plan_approved: "2026-11-21T14:05:00+00:00"   # when the human approved the plan (ISO 8601 with offset), or n/a when not required
base: 9fceb02d0ae598e95dc970b74767f19372d61af8   # the commit the run started from
trunk: origin/main            # the trunk ref; commits reachable from it are not the run's
reviewed_diff: "sha256:3b4c0f9a2e7d81c6f5a0e9d4b2c7a1f8e6d3c0b9a8f7e6d5c4b3a2f1e0d9c8b7"   # fingerprint of the change the last review saw
baseline_failures:            # tests already failing on the base before any change; [] when none
  - test: tests/test_net.py::test_fetch_ipv6
    signature: "ConnectionError: Network is unreachable"   # one redacted line: exception type or assertion message
selection:                    # optional: what each coordinator ran, per round ("Specialists", below)
  - pool: tester              # tester | reviewer
    round: 1
    tags: [untrusted-input, user-facing, regex]   # the effective tags: the plan's plus those the changed files showed
    chosen: [test-runner, check-runner, fuzzer]
    not_run:
      - specialist: mutation-tester
        reason: opt-in        # opt-in | budget
    budget:                   # what remained for this run of the pool
      heavy_runs: 6
      heavy_minutes: 60
    used:
      heavy_runs: 1
      heavy_minutes: 3
  - pool: reviewer
    round: 1
    tags: [untrusted-input, user-facing, regex]
    chosen: [correctness-reviewer, security-reviewer, docs-reviewer]
findings:                     # anything a later stage (or the human) had to catch or fix
  - stage: implement          # where the mistake was made: plan | test-write | implement | test | review
    category: generated-file-hand-edit   # kebab-case; reuse existing categories (see ledger) before inventing one
    severity: major           # minor | major | critical
    detail: "Edited the generated compose file instead of its source."
    caught_by: reviewer       # who noticed: test-writer | tester | reviewer | implementer | lead | human | ci | hook | check | self
    specialist: correctness-reviewer   # optional: the specialist that reported it, or a list when reports were merged
    fixed: true
rejected:                     # optional: findings a stage reported that turned out to be wrong
  - stage: review             # here: the stage that reported the wrong finding
    category: doc-drift
    specialist: docs-reviewer
    reason: "The README section it cited was updated in the same change."
notes: "Free text, optional."
```

Rules:
- `plan`, `plan_approved`, `base`, `trunk`, `reviewed_diff`, `baseline_failures` and the `preflight`, `test-write` and `gate` stages are written by the lead; older records without them stay valid (the gate check applies only to the record of the run being reported). `plan_approved` is `n/a` when approval was not required. `plan` is either the mapping above or a path to the plan record; its `verify_skills` and `tags` are optional (absent when none applied). `selection`, a finding's `specialist` and `report_only`, and a rejected entry's `specialist` are optional too ("Specialists", "In run records"). Each `baseline_failures` entry is a `test`/`signature` mapping; a bare test ID (the earlier form) stays valid but cannot tell a changed failure from the same one. The miner passes both through like any other field (redacted).
- Preflight mistakes (a stale trunk, a missed generator) are the lead's, so they are `stage: plan`. `stage: test-write` is a mistake the test-writer made (a test that cannot fail, or tests the wrong thing), whoever caught it.
- `category` is the unit of measurement. Prefer an existing category from the catalog (`docs/categories.md`), the ledger or earlier records; a new one is fine when nothing fits.
- A finding is something that went wrong and was caught by a *later* stage, the human, CI, a hook or a check, not a summary of the work. Mistakes an agent catches in its own work before reporting are not findings.
- `stage` is where the mistake was made, never who noticed it; `caught_by` is who noticed. A defect the tester or reviewer finds in the implementation is `stage: implement` with `caught_by: tester` or `caught_by: reviewer` (the pool), and `specialist` naming which of its specialists reported it. A missing or wrong acceptance criterion or verifier, a wrong plan or a bad brief (the lead's own mistakes) is `stage: plan`. `stage: test` and `stage: review` are only for mistakes the tester or reviewer pool made itself (a check skipped, a failure misreported) that someone else caught later. `caught_by: self` means the stage that made the mistake noticed it later in the run. A defect noticed by a different stage keeps the `stage` where it was made and has `caught_by` set to the stage that noticed it: `implementer` (or `test-writer`) when that agent finds a gap in the plan or contract it was given, `lead` when the lead catches a test-writer's, implementer's, tester's or reviewer's mistake (a test that cannot fail, a deviation, a misreported result). `caught_by: hook` is a hook that blocked the mistake; `caught_by: check` is a verify skill the tester's `check-runner` followed (below) that reported it. Those two tell a retro that a rule fired rather than that the mistake got past it.
- `outcome` is `completed` when the run finished and is waiting on the human, and `in-progress` only when it stopped part-way. The human's decision (`merged`, `reworked`, `abandoned`) replaces it when known.
- `rejected` records false positives, so a retro can measure how often a stage or specialist (usually a reviewer) is wrong; one that is often wrong is itself a candidate for a rule.
- Never put secrets, tokens, hostnames of private systems, or personal data in a record.

## Categories

The starting vocabulary of categories, each with its usual stage and the cheapest known rule, is `docs/categories.md` (`${CLAUDE_PLUGIN_ROOT}/docs/categories.md`). The lead and the retro read it and reuse its names before inventing new ones, so early runs count the same mistakes the same way. The retro may propose additions to it as framework-scope proposals.

## Gates

Two process categories are enforced, not just instructed, because instructions alone did not stop them. `scripts/record_gate.py` (standard library only; it runs read-only git commands, never writes the index, and writes nothing else) has two commands:

- `fingerprint --base <base>` prints a fingerprint of the change since `base`: `git diff --binary <base>` (committed and uncommitted tracked changes) plus every untracked file's path and content, leaving out `.claude/runs/`. The lead runs it when it briefs the reviewer and records the last one as `reviewed_diff`.
- `check <record>` checks the record before the lead reports done, reading `base`, `trunk` and `reviewed_diff` from it (`--base` and `--trunk` override):
  - `skipped-independent-review`: the change's fingerprint now equals `reviewed_diff`, so the final diff is the one reviewed. A record without `reviewed_diff` falls back to the stage order: a `review` after the last `implement` or `test-write`.
  - `skipped-plan-approval`: `plan_approved` is an ISO 8601 date-time with a UTC offset, or `n/a`; with `--require-plan-approval` (approval was required), `n/a` fails. With a `base`, none of the run's own commits (`base..HEAD`, skipping merges and anything reachable from `trunk`) is authored before `plan_approved`.

Exit codes, and what the lead does:

| Code | Meaning | The lead |
|---|---|---|
| 0 | pass | reports done |
| 1 | review missing or stale | reviews the final diff if rounds remain, else stops and reports the run as not done |
| 3 | plan approval skipped | stops and reports to the human: rerunning cannot fix it |
| 2 | cannot check: git missing, not a repository, unknown `base` or `trunk`, `base` no longer an ancestor of `HEAD` (re-record it after a rebase), unparsable git output, unreadable record | reports why and stops; never loops |

When several apply, 3 wins over 2, and 2 over 1. Records with `outcome: in-progress` or `abandoned` are not done reports and are not gated.

Limits: the commit check sees only commits, so when the run leaves its change uncommitted the approval check rests on the record alone. Author dates are advisory: a rebase with `--reset-author` or `--ignore-date` rewrites them. The gates are a script the lead runs, not a hook: a hook would also fire on the human's ordinary work outside a lead run.

## Specialists

The test and review stages are run by two coordinator agents, each over a pool of specialist agents. A coordinator chooses specialists for the change, runs them, merges their reports and returns one report to the lead. Each specialist does one kind of check with a narrow brief and the narrowest tools that work. The coordinators keep the names of the agents they replaced, so `caught_by: tester` and `caught_by: reviewer` mean the same pools as before.

```
lead ──► agent-loop:tester (verification: runs things, collects evidence)
           test-runner · measurement-auditor · check-runner · fuzzer · api-fuzzer
           mutation-tester · system-tester · perf-tester · security-scanner
     ──► agent-loop:reviewer (review: reads the code, judges it)
           correctness-reviewer · security-reviewer · permissions-reviewer
           api-reviewer · docs-reviewer
```

### The two pools

| Specialist | Pool | Weight | Does |
|---|---|---|---|
| `test-runner` | tester | heavy | Runs the criteria's verifiers and the project's tests, build, lint and type checks against the baseline (PRE-EXISTING versus new failures). |
| `measurement-auditor` | tester | heavy | Applies the measurement invariants and run hygiene (below) to a change touching tests or measurement; reports unit and integration coverage apart. |
| `check-runner` | tester | light | Follows the plan's verify skills on the change, read-only ("Verify skills", below). |
| `fuzzer` | tester | heavy | Times new or changed regular expressions on adversarial input; runs the project's property and fuzz tests for the changed code. |
| `api-fuzzer` | tester | heavy | Fuzzes the changed operations against the project's API spec (OpenAPI, AsyncAPI): a 500 or a schema break is a finding. |
| `mutation-tester` | tester | heavy | Mutation testing scoped to the diff: a surviving mutant in changed code is a test that proves too little. |
| `system-tester` | tester | heavy | System and end-to-end tests, and running the app for real where the project documents how. |
| `perf-tester` | tester | heavy | The project's benchmarks or a timed run of the changed path, against the baseline. |
| `security-scanner` | tester | heavy | The project's SAST rules and dependency scan. |
| `correctness-reviewer` | reviewer | light | Logic, unmet criteria, scope, weakened or hand-edited files, against the criteria and the rules brief. |
| `security-reviewer` | reviewer | light | How an attacker could abuse the change: injection, traversal, authorisation, secrets, redaction. |
| `permissions-reviewer` | reviewer | light | The least-privilege check on every permission entry the change touches. |
| `api-reviewer` | reviewer | light | Compatibility of public interfaces and the contract between components. |
| `docs-reviewer` | reviewer | light | Docs and contract drift: every other description of a changed behaviour still matches. |

Each specialist's own categories (the ones it should catch, which the retro's miss rate uses) are in `docs/selection.yml`. Verification specialists end with the shared verifier report (each check PASS, FAIL, PRE-EXISTING, BLOCKED or UNVERIFIED, with trimmed evidence); review specialists with the shared review report (each finding with category, severity, `file:line` and a concrete failure scenario, or "no findings"). No specialist name starts with `verify-`: that prefix is a project's verify skills.

Every specialist that runs tools has the same rules: it never edits the repository (temporary files outside it only, removed afterwards), never installs anything, runs multi-step commands with `bash -c`, wraps long commands in `timeout`, cleans up after an aborted heavy run, and reports a missing tool, spec, credential or service as BLOCKED, naming what is missing. Those gaps are what a readiness audit of the repository measures; the specialist does not close them. Diff-scoped work reads the change since the run's `<base>` (the merge base the lead recorded), never a hard-coded default branch, so stacked branches work.

At least one check in every run works from the criteria and not from the implementation: the test-writer's tests, and the reviewers, who get the criteria and the diff but never the implementer's reasoning. Green checks that share the code's own wrong assumptions are the trap this guards against.

### Risk tags and the baseline

While planning, the lead tags each unit with the risk tags that apply (`plan.tags` in the run record). Every run gets the **baseline**, `test-runner` and `correctness-reviewer`, whatever the tags. A coordinator also adds tags the changed files show the lead missed: `test-infra` for tests, fixtures, test config, coverage or CI test jobs; `permissions` for `allowed-tools`, agent `tools`, settings permissions or hooks, CI tokens; `dependencies` for manifests and lockfiles; `regex` for a changed file that defines a regular expression. It says which it added. `check-runner` runs whenever the plan chose verify skills.

### The selection table

The default table, `docs/selection.yml` (`${CLAUDE_PLUGIN_ROOT}/docs/selection.yml`), maps each tag to the specialists it adds to the baseline:

| Tag | When | Adds |
|---|---|---|
| `untrusted-input` | Parses, decodes or acts on input from outside the trust boundary: requests, files, arguments, messages, environment. | `fuzzer`, `security-reviewer` |
| `security-sensitive` | Auth, sessions, secrets, crypto, redaction or sanitising, path handling: code an attacker would target. | `security-scanner`, `mutation-tester`, `security-reviewer` |
| `permissions` | Changes who or what may do something: allowed-tools, agent tools, settings permissions or hooks, CI tokens, roles, access rules. | `permissions-reviewer` |
| `data-migration` | Changes stored data or its format: migrations, schema changes, backfills, formats older code still reads. | `system-tester`, `mutation-tester`, `api-reviewer` |
| `public-api` | Changes an interface others depend on: a public function, HTTP API, CLI, events, a contract between components. | `api-fuzzer`, `api-reviewer`, `docs-reviewer` |
| `concurrency` | Threads, async, locks, queues, retries, or state shared by more than one worker. | `system-tester` |
| `perf-sensitive` | Hot paths, loops over unbounded data, queries, caching, or a stated latency or size limit. | `perf-tester` |
| `ui` | What a user sees or does in a browser or app. | `system-tester` |
| `test-infra` | Tests, fixtures, test config or runners, coverage or other measurement, CI test jobs. | `measurement-auditor` |
| `regex` | Adds or changes a regular expression or another backtracking matcher. | `fuzzer` |
| `dependencies` | Adds, removes or upgrades a dependency or lockfile. | `security-scanner` |
| `user-facing` | Changes behaviour something else describes: options, defaults, output, errors, documented steps. | `docs-reviewer` |

**Opt-in and report-only.** New checks must not make the default run slower or fail work they were not meant to gate yet. So `api-fuzzer`, `mutation-tester`, `system-tester`, `perf-tester` and `security-scanner` are `opt_in`: a tag that selects one does not run it unless the project enables it (below). The coordinator lists it as not run, reason `opt-in`. An enabled opt-in specialist starts **report-only**: its findings are recorded (`report_only: true`) and shown to the human, but they do not start a fix round or block "done" until the project lists it under `blocking`.

**A project's override** lives in `<repo>/.claude/agent-loop/selection.yml`, with the same shape:

```yaml
schema: 1
enable: [mutation-tester]     # opt-in specialists this project runs
blocking: [mutation-tester]   # enabled ones whose findings block like any other
budget:
  heavy_runs: 4               # replaces the default
tags:
  data-migration:             # a known tag: the fields given replace the default row's
    run: [system-tester, api-reviewer]
  sql-migrations:             # a project tag needs both fields
    when: "Adds or changes a file under migrations/."
    run: [system-tester]
```

It cannot change the baseline or the specialists. Anything invalid (an unknown specialist, `blocking` for one that is not enabled, a new tag without `when`) is ignored and reported; the coordinator says so, and the retro's miner reports it under `specialists.selection.errors`. Overrides are rules: the retro proposes them behind the human gate, with a ledger entry (below).

### Running them

- The coordinator states the effective tags, the specialists it chose and why (the baseline, which tag, verify skills), and those it did not run and why (`opt-in`, `budget`).
- With no tags and no override file, a coordinator runs the baseline (and `check-runner` for verify skills) without reading the table, so the baseline path stays cheap.
- Light specialists start together, in parallel. Heavy ones (anything that runs a full suite, mutation testing, fuzzing, system or performance runs) run one at a time, never two at once, and never while another heavy job of the run is going.
- **Budget**, per lead run, for heavy specialists beyond the baseline: `heavy_runs` runs and `heavy_minutes` minutes of their wall time across all rounds (defaults 6 and 60; the project's override or the task text can change them). The lead passes what remains to the tester coordinator, which does not start a heavy specialist the remaining runs cannot cover and gives each one the remaining minutes as its time limit. One not started is listed as not run, reason `budget`; the lead asks the human whether to raise the budget rather than dropping it silently. The record's `selection` shows the budget and what was used.
- Specialists report to the coordinator, never to the lead. The coordinator merges findings that are the same defect (same location and cause), keeping the highest severity and every specialist that reported it, and returns one report.
- In a later round the coordinator runs its selection again on the whole change; the budget still covers the whole run.

The coordinators' tools are `Agent`, `Read`, `Glob` and `Grep`: they read the brief, the table and the specialists' reports, and start specialists. A plugin agent with `Agent` can start other plugin agents. Its `tools` field cannot limit which ones: an `Agent(<type>)` entry is accepted but, for a subagent, does not restrict the types it starts (checked on Claude Code 2.1.322), so a coordinator starts only `agent-loop` specialists of its own pool by instruction. Specialists have no `Agent` tool, so the tree is two levels deep.

### In run records

`plan.tags` holds each unit's tags; `selection` holds, per coordinator and round, the effective tags, the specialists chosen, those not run with the reason, the budget and what was used; a finding carries `specialist` (one name, or the list of those whose reports were merged) besides `caught_by` (the pool: `tester` or `reviewer`, or `check` for a verify skill); `report_only: true` marks a finding from an enabled opt-in specialist that is not blocking. A `rejected` entry carries `specialist` too, so precision can be measured. All are optional; records without them stay valid. A verify skill's FAIL is `caught_by: check` with `specialist: check-runner`.

### The ledger governs the table

A change to the selection table is a rule: the retro proposes it in the project's override file behind the human gate, with a ledger entry `rung: selection`, the `category` it targets, the `specialist` it adds or removes and `location: ".claude/agent-loop/selection.yml"`. It is verified like any rule: for a `selection` rule, a finding in its category that its specialist reported counts as `caught_by_rule`, and everything else escaped it. Changes to the plugin's default table are framework proposals.

The retro measures each specialist from the run records: per specialist and per tag, the runs that chose it, its findings, its rejected findings (precision: findings over findings plus rejected) and its misses (a finding in one of its own categories, in a run that chose it, that it did not report; miss rate: misses over findings plus misses); and per tag, the categories that escaped to the human or CI. A specialist that never catches anything for a tag is a candidate to drop from it; a category that escapes runs with a tag is a candidate for adding the specialist that owns it.

## Measurement invariants

Verifiers distrust results that look too good or too bad: a loop on a flaky or contaminated measurement costs more than the bug it was looking for. The `measurement-auditor` specialist applies these whenever a unit is tagged `test-infra` (the diff touches tests, fixtures, test configuration or runners, coverage or other measurement, or CI test jobs). Categories are from `docs/categories.md`.

| Invariant | Category |
|---|---|
| A subset run never beats the full run (pass count, coverage). | `measurement-attribution-leak` |
| Coverage credits a line only when it runs inside a test body, not during setup or import. | `measurement-attribution-leak` |
| Order independence: failing in the full run and passing alone is an isolation bug; report it, never rerun until green. | `shared-state-false-failures` |
| A wall of failures means shared state broke until shown otherwise; investigate the first failure. | `shared-state-false-failures` |
| Tests act as the real client: its role and auth identity, not a convenient token. | `wrong-auth-identity` |
| No silent allowlists: known failures are listed, each with a reproduction. | `silent-allowlist` |
| New checks are opt-in locally and report-only in CI at first (unless a criterion asks otherwise); the default test run gets no slower than the baseline. | `new-check-not-opt-in` |

Run hygiene, which every verification specialist applies to every run:

| Rule | Category |
|---|---|
| After an aborted heavy run, remove what it started (containers, worktrees, temporary databases) and confirm nothing is left. | `leftover-resources` |
| Run multi-step scripts with `bash -c`, so behaviour does not depend on the interactive shell. | `shell-portability` |

When the data cannot tell whether an invariant holds, the auditor reports it UNVERIFIED rather than changing configuration to find out. The opt-in rule gives way when an acceptance criterion asks for a blocking or default-on check; "no slower" is measured against the baseline run's wall time, which the lead notes at preflight. Where coverage is measured, the auditor reports unit and integration coverage apart, classifying a test by the fixtures it really depends on (one holding a database or a client makes it an integration test; autouse fixtures are left out), not by markers: mutation testing reaches only pure tests and coverage overstates code only integration tests touch, and those blind spots overlap on the riskiest code.

## The promotion ladder

| Rung | When |
|---|---|
| `note` | Seen once: it stays in the run record; no rule yet. |
| `instruction` | Seen twice, or once at `critical` severity: a line in CLAUDE.md, a skill, or memory. |
| `check` | Recurs after an `instruction` exists, needs judgment to verify, and can be written as a repeatable procedure: a verify skill (below) that the tester's `check-runner` follows. |
| `hook` | Recurs after an `instruction` (or a `check`) exists, and can be checked mechanically: a hook or CI check that blocks it. |
| `test` | The mistake is about behaviour of the code, not process: a test or eval that fails on it. |

A `selection` ledger entry is not a rung of the ladder: it records a change to which specialists run for a tag ("Specialists", "The ledger governs the table"), verified the same way.

Verification on each retro, for every ledger rule. Occurrences are counted strictly after `added` (a record dated the same day as the rule predates it), from run-record findings plus transcript signals the retro assigned to the category. The windows:
- Run records are small, so the miner reads all of them (from every worktree of the project) whatever `--since` says; a rule's run-record occurrences cover everything since its `added` date. Only `category_counts` is limited to the requested window.
- Transcript signals cover the requested window, extended back automatically to the `added` date of the oldest rule in either ledger, but never more than 90 days before the retro. A rule older than that is checked against the last 90 days of transcripts only. The miner reports the windows it actually used under `window`.

Escapes, not catches, count against a rule. For a `hook` or `check` rule the miner splits `occurrences_since` (the total) into `caught_by_rule`, the findings whose `caught_by` is the rule's own rung (`hook` or `check`), and `escaped`, the rest; for a `selection` rule, `caught_by_rule` is the findings its `specialist` reported. For other rungs a catch cannot be told apart from an escape, so every occurrence is `escaped`. Transcript signals the retro assigns to the category are escapes too.

Verdicts:
- `working`: nothing has escaped the rule since it was added (`escaped` is 0). Catches are evidence that it fires, not a recurrence. A rule that catches constantly may sit on an unclear instruction upstream; the retro may say so, but does not escalate it.
- `recurring`: something escaped it (`escaped` > 0). Propose the next rung up (or a rewrite, if the rule is unclear). From `check`, the next rung is a `hook` or a `test` where the check can be made mechanical; otherwise a rewrite of its procedure (below). The commit adding the higher-rung rule also sets the old rule's `superseded_by` to the new rule's id; a rewrite changes the rule in place.
- `superseded`: the rule has `superseded_by`, the id of the higher-rung rule that escalated it. It is still reported, with its counts, but never escalated again; the rule that replaced it carries the category from then on.
- `dormant`: the rule is at least 90 days old and no work in that time touched what it governs, so there was nothing for it to prevent. The miner reports `days_since_added` and `records_since_added`; the retro judges relevance. Propose retiring it, so instructions don't accumulate forever.

Transcript signals arrive uncategorized; the retro assigns each a category (reusing existing ones) or discards it as a false positive before counting. A user ledger is checked against the run records of whichever project the retro runs in.

## Verify skills (the `check` rung)

A verify skill turns a check that needs judgment into a procedure that runs every time, instead of relying on an instruction being remembered. It is an ordinary Claude Code skill in the project or user scope; it reports violations and never fixes them. It is read-only by rule, not by its tools: its pre-approvals allow no writes, but a step could still ask for one, so the `check-runner` specialist enforces the rule ("In a lead run", below).

**Choosing the rung.**
- `instruction` first: telling the agent is the cheapest rule, and most categories stop there.
- `check` when the category recurred with the instruction in place, deciding whether a change violates the rule takes judgment (reading the change and its context, not matching a path or a command), and the decision can be written as steps that anyone following them would apply the same way. For example: every migration that drops a column has a backfill step; a change to a public interface has a changelog entry.
- `hook` instead, when the tool call alone shows the mistake (its path, command or content), with no judgment.
- `test` instead, when the mistake is in the code's behaviour. A test or hook beats a check wherever one can be written.

**Shape.** One skill per category, at `.claude/skills/verify-<category>/SKILL.md` (project) or `~/.claude/skills/verify-<category>/SKILL.md` (user). The retro's template is `skills/retro/references/verify-skill.md`; a worked example is `docs/examples/verify-doc-drift/SKILL.md` (a document, not a plugin skill).
- `name`: `verify-<category>`, the category from the catalog, the ledger or earlier records.
- `description`: what it checks, then a "Use when ..." clause naming the files or kinds of change it applies to.
- `paths` (recommended): globs of the files it applies to. The lead selects on them, and Claude Code offers the skill only when work touches matching files.
- `allowed-tools`: the narrowest read-only set that works, which must pass the permissions reviewer's least-privilege check (`over-broad-pre-approval`): `Read`, `Grep`, `Glob`, and at most the exact read-only command `Bash(git status --porcelain)`. Never `Write` or `Edit`, a Bash entry with a wildcard (it can absorb a writing flag such as `--output=<file>`), or network access. Diffing against a base cannot be pre-approved without a wildcard, so it asks when the skill runs on its own.
- Body: the input (the change since a base commit: the one the caller names, else `git merge-base HEAD origin/<default>`; never `HEAD` alone, whose diff is empty once the work is committed), the procedure as numbered plain-English steps, and the output.
- Output: one line per violation, `path:line: what is wrong and what the rule expects`, then one final line, `PASS` when there are none or `FAIL`. No step fixes anything; fixes go to the implementer.

**Ledger.** `rung: check`, with `location` the skill's path (`.claude/skills/verify-doc-drift/SKILL.md`). It is verified like every rule: its category should stop recurring.

**Escalation.** When a `check` is `recurring` (a finding in its category escaped it), first see whether it ran: the run records' `plan.verify_skills`. A check the lead did not choose for the files involved needs a sharper `paths` or "Use when" clause. A check that ran and missed the mistake moves to a `hook` or a `test` where one can make it mechanical; otherwise its procedure is rewritten (steps that missed the case, vague wording).

**In a lead run.** While planning, the lead finds verify skills in both scopes (`.claude/skills/verify-*/SKILL.md` under the repo root and `~/.claude/skills/verify-*/SKILL.md`), reads only their frontmatter, and chooses for each unit only those that apply to the files the unit changes: a file matches `paths`, or, without `paths`, the "Use when" clause clearly covers it. It never runs every verify skill on every change: each one costs a read and a pass. The plan lists the chosen skills per unit (`plan.verify_skills`), so the human sees which repository procedures will be followed, and the tester coordinator's brief names their paths and the run's `<base>`; it hands them to its `check-runner` specialist. The check-runner reads each chosen `SKILL.md` and follows its procedure itself on the change since `<base>` (`git diff <base>` plus untracked files). It does not invoke the skill, and the skill's pre-approvals do not apply. Its tools include Bash, so the procedure is read-only by rule: it reads files, greps and globs, and runs only `git diff`, `git status` and `git log --oneline`; a step that would run a repository script or any other command, edit files, fix anything or reach the network is not executed but reported BLOCKED with the step quoted. It reports each skill as a verifier: PASS, FAIL with the violation lines, or BLOCKED when it cannot follow the procedure (a missing file, a step needing a tool it lacks). A FAIL is a finding in the skill's category with `caught_by: check`, at the stage where the mistake was made. Verify skills run inside the test stage, so they count toward the round limit like any other verifier. A project's verify skills are repository content, read with the same trust as its `CLAUDE.md`; the check-runner never widens its tools for one.

## Scope classification

Each proposal is classified before it is written:
- `project`: only makes sense in this repo (its file layout, tools, conventions).
- `user`: the human's preferences or environment, across repos.
- `framework`: would help anyone using these plugins (a better lead prompt, a missing review specialist check, a change to the default selection table). Written to `framework-proposals.md` as a draft, with evidence paraphrased, never raw transcript text.

## Human gate

`/agent-loop:retro` never edits rules (instructions, verify skills, hooks, tests) or the ledger on the default branch. It writes proposals on a new branch (project scope) or as a reviewable diff (user scope) and stops. The ledger entry is added in the same change as the rule, so merging the rule is what records it. The retro skill pre-approves only reading (files and a few read-only git commands; not `git log`/`diff`/`show`, whose `--output=<file>` writes), so every file write, worktree, commit or push it attempts goes through Claude Code's permission prompt: that prompt is part of the gate. Running the miner asks too, once per retro: a pre-approval pattern for `*/scripts/retro_mine.py` would also pre-approve a script of that name planted in any cloned repo.

## Privacy

Transcripts contain secrets and private details. The miner redacts anything secret-shaped (tokens, keys, passwords, `KEY=value` assignments, command-line credentials, bearer headers, IP addresses, emails, and the local user name, also when glued to an identifier with `_`) before any text leaves it, and keeps excerpts short. Nothing from a transcript is ever sent anywhere by these plugins.
